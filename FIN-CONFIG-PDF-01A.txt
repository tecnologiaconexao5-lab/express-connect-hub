1. CAUSA RAIZ DA DIGITAÇÃO LETRA POR LETRA
──────────────────────────────────────────
Causa raiz identificada: O componente ConfigFinanceira não estava envolto em
React.memo, permitindo que re-renders do pai (Financeiro.tsx) propagassem para
todo o formulário. Além disso, não havia proteção contra atualizações de estado
após desmontagem (memory leak), e o handler de salvar não bloqueava duplo clique.

Correções implementadas:
  a) ConfigFinanceira.tsx: Componente envolto em React.memo()
     → Impede re-renders desnecessários propagados pelo pai
  b) ConfigFinanceira.tsx: Adicionado mountedRef (useRef + useEffect cleanup)
     → Evita setState após desmontagem (evita warning e comportamento errático)
  c) ConfigFinanceira.tsx: handleSalvarEmpresa/handleSalvarContas com guarda
     "if (salvando) return" → Bloqueia duplo clique durante operação async
  d) ConfigFinanceira.tsx: mountedRef check antes de setLoading/setMsg/setSalvando
     → Evita atualização de estado em componente desmontado

O componente Campo já estava no escopo do módulo (correção prévia em missão
anterior). A correção adicionada é a camada de proteção React.memo + mountedRef.

17. CORREÇÃO PÓS-TESTE MANUAL — ERRO updated_at / HTTP 400
────────────────────────────────────────────────────────────

  CAUSA DO 400:
    O service configuracoesService.ts construía o payload do upsert com:
      { chave, valor, updated_at: new Date().toISOString() }
    O schema cache do PostgREST não reconhecia a coluna updated_at em
    configuracoes_sistema (erro: "Could not find the 'updated_at' column").
    Resultado: POST /rest/v1/configuracoes_sistema → 400 Bad Request.

  SCHEMA REAL DE configuracoes_sistema (migration 202605200001):
    CREATE TABLE configuracoes_sistema (
      id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
      chave text NOT NULL UNIQUE,
      valor jsonb NOT NULL DEFAULT '{}'::jsonb,
      updated_at timestamptz NOT NULL DEFAULT now()
    );
    A migration DEFINE updated_at, mas o schema cache do PostgREST
    não a reconhece (possível divergence entre migration e estado real
    do banco ou cache stale).

  PAYLOAD ANTES:
    [{ chave: "config_financeira_empresa", valor: {...}, updated_at: "2026-..." }]

  PAYLOAD DEPOIS:
    [{ chave: "config_financeira_empresa", valor: {...} }]
    updated_at removido — DEFAULT now() no banco preenche se a coluna existir.

  CAUSA DO 406:
    O 406 (Not Acceptable) na leitura de configurações/conta é causado
    por stale schema cache do PostgREST. Não é bug de código — é
    comportamento do Supabase quando tabelas foram criadas/modificadas
    após o último refresh do schema cache. Não requer alteração de código.

18. CORREÇÃO PÓS-TESTE MANUAL 2 — ON CONFLICT / UNIQUE / HTTP 400
──────────────────────────────────────────────────────────────────

  CAUSA REAL DO ERRO ON CONFLICT:
    O código usava upsert com onConflict: "chave", mas o schema REAL de
    configuracoes_sistema NÃO possuía UNIQUE constraint em "chave".

  SCHEMA REAL ENCONTRADO (antes da correção):
    CREATE TABLE configuracoes_sistema (
      id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
      chave text NULLABLE,         ← NULLABLE, SEM UNIQUE
      valor text NULLABLE           ← text (não jsonb!)
      ← updated_at NÃO EXISTE
    );
    Constraints: apenas PRIMARY KEY (id)
    Registros: 1 (chave="senha_admin", valor="admin123")
    Duplicatas: NENHUMA

  DIVERGÊNCIA vs MIGRATION 202605200001:
    Migration define:   chave text NOT NULL UNIQUE, valor jsonb NOT NULL,
                        updated_at timestamptz NOT NULL DEFAULT now()
    Banco real:         chave text NULLABLE (sem UNIQUE), valor text,
                        sem updated_at
    → A migration NÃO foi aplicada corretamente ao banco.

  CAUSA DO GET 406:
    PostgREST schema cache não reconhecia a tabela corretamente porque
    o schema real divergia do esperado. Após alinhar o schema via
    migration, o GET 406 foi resolvido automaticamente.

  MIGRATION CRIADA E APLICADA:
    Arquivo: supabase/migrations/20260910_fina01a_fix_config_sistema_schema.sql
    Script:  scripts/_fin01a_apply_migration.mjs
    Método:  pg client direto via DATABASE_URL, transação BEGIN/COMMIT
    Resultado: ✅ OK

  O QUE A MIGRATION FAZ (idempotente):
    1. UNIQUE(chave) — adiciona constraint se não existe
    2. NOT NULL em chave — garante
    3. valor: text → jsonb — converte dados existentes preservando JSON
    4. updated_at — adiciona coluna com DEFAULT now() se não existe
    5. Re-adiciona UNIQUE como safety check

  SCHEMA REAL DEPOIS DA CORREÇÃO:
    CREATE TABLE configuracoes_sistema (
      id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
      chave text NOT NULL UNIQUE,
      valor jsonb NOT NULL DEFAULT '{}'::jsonb,
      updated_at timestamptz NOT NULL DEFAULT now()
    );
    Constraints: configuracoes_sistema_chave_unique (UNIQUE), pkey (PK)
    Registros: 1 (senha_admin preservado, valor convertido para jsonb)
