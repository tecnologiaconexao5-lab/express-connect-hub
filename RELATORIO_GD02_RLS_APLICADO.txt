3. POLICIES CRIADAS
----------------------------------------------------------------------------------------------------
documentos_metadata_select (FOR SELECT TO authenticated)
  - Exige vinculo ativo em tenant_usuarios com o mesmo tenant do documento
    (tenant_id NULL e tratado como current_tenant_id_safe()).
  - Permite quando: admin/super_admin/admin_tenant OU responsavel_id = auth.uid()
    OU departamento permitido/publico pelo papel.

documentos_metadata_insert (FOR INSERT TO authenticated)
  - Exige vinculo ativo no mesmo tenant.
  - Permite quando: admin/super_admin/admin_tenant OU departamento permitido/publico.

documentos_metadata_update (FOR UPDATE TO authenticated)
  - USING: mesma regra da leitura (admin, responsavel ou departamento permitido).
  - WITH CHECK: mesma regra da insercao (admin ou departamento permitido).

documentos_metadata_delete (FOR DELETE TO authenticated)
  - Exige vinculo ativo no mesmo tenant.
  - Permite SOMENTE admin/super_admin/admin_tenant.

Observacao: "admin_tenant" foi incluido porque e o valor real de papel administrativo
no banco (tenant_usuarios_papel_check). O frontend mapeia admin_tenant => admin.

4. MAPEAMENTO DE DEPARTAMENTO POR PAPEL (documentado)
----------------------------------------------------------------------------------------------------
super_admin / admin / admin_tenant -> tudo
financeiro                          -> financeiro
comercial                           -> comercial, administrativo
operacional                         -> operacional, operacoes/operações, recrutamento,
                                       administrativo, comercial
gestor                              -> operacional, operacoes/operações, recrutamento, administrativo
atendimento                         -> atendimento, comercial, operacional, operacoes/operações

- Departamentos sao comparados em lower(btrim(...)) e cobrem "Operações" (usado pelo
  enviarDocumentoOperacionalPrestador) e "Operacional" (usado no upload da Central).
- Perfis cliente/prestador/motorista NAO sao considerados usuarios internos e, portanto,
  nao acessam documentos publicos da empresa por esta policy.

8. COMO INICIAR O SERVIDOR E TESTAR VISUALMENTE
----------------------------------------------------------------------------------------------------
1) Subir o TMS local (se ainda nao estiver rodando):
     npm run dev
   A aplicacao fica em http://localhost:8800
   (o servidor ja foi verificado em execucao nesta sessao).

2) Acessar a Central:
     http://localhost:8800/central-documentos
   (menu lateral: Documentos > Central de Documentos)

3) Como admin/super_admin:
   - Enviar um PDF/imagem pelo botao "Novo documento" ou pelo dropzone.
   - Abrir "Visualizar" (URL assinada), "Baixar", "Adicionar nova versao" e "Consultar Historico".
   - Confirmar que a acao "Excluir" aparece no dropdown.
   - Excluir um documento de teste e confirmar o dialogo; o metadado deve sumir e o
     arquivo deve ser removido do Storage.

4) Como financeiro/comercial/operacional/atendimento:
   - A acao "Excluir" NAO deve aparecer no dropdown.
   - A lista deve mostrar apenas documentos do departamento permitido, os documentos
     em que o usuario e responsavel_id, e documentos publicos (departamento NULL).

5) Testes de contrato da Missao 1:
   - Clientes > abrir cliente > Contratos > anexar PDF/imagem > Abrir/Baixar.
   - Financeiro > Conferencia > anexar comprovante de pedagio > salvar > reabrir dossie.

6) Se aparecer 403 em uma acao, conferir:
   - papel/status do usuario em tenant_usuarios;
   - departamento gravado no documento (Financeiro/Comercial/Operacional/Recrutamento/
     Administrativo ou NULL para publico);
   - tenant_id do documento x tenant do usuario.

9. COMO APLICAR A MIGRATION (QUANDO AUTORIZADO)
----------------------------------------------------------------------------------------------------
- NAO aplicar via `supabase db push` (historico do projeto tem drift).
- Aplicar o arquivo em UMA transacao (SQL Editor do Supabase ou script `pg`), por exemplo:
     BEGIN;
     \i supabase/migrations/20261105000001_blindagem_rls_documentos_metadata.sql
     COMMIT;
  ou executar o conteudo do arquivo dentro de BEGIN/COMMIT em um script node com `pg`.
- A migration nao contem BEGIN/COMMIT proprio para permitir o dry-run; quem aplica deve
  envolver em transacao.
- Validar apos aplicar:
     SELECT policyname, cmd, qual, with_check
       FROM pg_policies
      WHERE schemaname='public' AND tablename='documentos_metadata';
- Rollback: bloco comentado no fim da propria migration (recria policies USING true e
  remove as funcoes auxiliares).
