CONCLUSÕES:

  A) VALOR DEVIDO = cada linha de pagamentos_prestadores com status=pago? NÃO.
     Cada linha representa um SERVIÇO/REPASSE. O valor devido é o valor_liquido
     da linha. O que a empresa DEVE ao prestador é a SOMA de valor_liquido de
     todas as linhas pendentes daquele prestador no período.

  B) FECHAMENTO = agrupamento de múltiplos serviços/repasses em um único
     registro-mãe (tipo_pagamento="fechamento") que representa o total a pagar
     para um prestador em um período. Itens ficam vinculados via fechamento_id.

  C) PAGAMENTO = transição de status_pagamento de pendente para pago.
     Produz consequência na Conta Corrente (débito = valor pago).

  D) BAIXA = gravação em financeiro_baixas (RPC f_confirmar_pagamento_prestador).
     Não acessível via anon (RLS bloqueia).

  E) EVIDÊNCIA DE PAGAMENTO = status_pagamento = "pago" + data_pagamento preenchida.

3. FECHAMENTO — ARQUITETURA IMPLEMENTADA
================================================================================

3.1 — SCHEMA (migration 20260911_fin_p1_03_fechamento_prestador.sql)

  Colunas adicionadas a pagamentos_prestadores:
    fechamento_id UUID NULL — FK auto-ref para id do fechamento-mãe
    data_conferencia TIMESTAMPTZ NULL — snapshot de conferência
    data_aprovacao TIMESTAMPTZ NULL — snapshot de aprovação

  Constraints:
    fk_fechamento_pai — FK(self) ON DELETE SET NULL

  Índices:
    idx_pp_fechamento_id — buscas rápidas por fechamento
    idx_pp_fechamento_tipo — lookup de fechamentos por tipo+prestador+período

3.2 — SERVICE (fechamentoService.ts)

  Funções:
    criarFechamento() — agrupa itens, cria registro-mãe, vincula
    buscarFechamento() — retorna fechamento com itens detalhados
    listarFechamentos() — filtros por prestador, status, período
    conferirFechamento() — EM_CONFERENCIA → CONFERIDO (snapshot data_conferencia)
    aprovarFechamento() — CONFERIDO → APROVADO (snapshot data_aprovacao)
    pagarFechamento() — APROVADO → PAGO (idempotente: segunda chamada = no-op)
    cancelarFechamento() — qualquer → CANCELADO (desvincula itens)
    itemEmFechamentoAtivo() — verifica se item já está em fechamento ativo

3.3 — FLUXO DE ESTADOS

  ┌──────────────┐    conferir()    ┌──────────────┐
  │EM_CONFERENCIA│ ───────────────→ │  CONFERIDO   │
  └──────────────┘                  └──────────────┘
        │                                   │
        │ cancelar()                        │ aprovar()
        ↓                                   ↓
  ┌──────────────┐                  ┌──────────────┐
  │  CANCELADO   │                  │   APROVADO   │
  └──────────────┘                  └──────────────┘
        │                                   │
        │ (terminal)                        │ pagar()
        │                                   ↓
        │                            ┌──────────────┐
        │                            │     PAGO     │
        │                            └──────────────┘
        │                                   │
        │                            (terminal, idempotente)
        │

  Transições permitidas:
    em_conferencia → conferido, cancelado
    conferido → aprovado, cancelado
    aprovado → pago, cancelado
    pago → (nenhuma)
    cancelado → (nenhuma)

3.4 — SNAPSHOT

  Fechamento preserva no momento da criação:
    - valor_servicos (soma dos itens)
    - valor_reembolsos, valor_bonus, valor_descontos, valor_adiantamentos
    - pedagio, adicionais, descontos
    - valor_liquido (total)
    - quantidade_itens (qtd_os)

  Após criação:
    - data_conferencia: timestamp de quando foi conferido
    - data_aprovacao: timestamp de quando foi aprovado
    - data_pagamento: data do pagamento

  Proteção: valores do fechamento-mãe NÃO são recalculados
  automaticamente. Alteração de cadastro do prestador não muda
  fechamento já criado.

5. PAGAMENTO
================================================================================

5.1 — Pagamento confirmado:
      1. Identifica fechamento (via ID)
      2. Registra valor efetivamente pago (valor_liquido do fechamento)
      3. Registra data_pagamento
      4. Registra conta_financeira_id (opcional)
      5. Produz consequência: status_pagamento = "pago" no fechamento
         E em todos os itens vinculados
      6. Trilha auditável em observacao

5.2 — Idempotência:
      Segunda confirmação de pagamento = NO-OP (retorna fechamento
      sem erro). Implementado em pagarFechamento():
        if (atual.status_pagamento === "pago") return buscarFechamento(...)

5.3 — FALTA EM PRODUÇÃO:
      A RPC f_confirmar_pagamento_prestador NÃO foi modificada nesta
      missão. Ela grava financeiro_baixas. Para fechamento completo,
      necessário:
      - Criar RPC específica para fechamento (itera itens)
      OU
      - Chamar confirmarPagamento() para cada item individualmente

      ISTO É UMA PENDÊNCIA P2 (documentada no relatório).
