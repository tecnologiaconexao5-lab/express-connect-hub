4. ANALISE DE COMPATIBILIDADE COM O BUG
============================================================

BUG DOCUMENTADO (supabase/cli PR #5895):
  "The TS role step-down was lost mid-command... PgClient.make
   leaves node-postgres' default 10s idle timeout — during the
   minutes-long shadow diff the pool silently reaped and redialed
   the stepped-down connection, so the final CREATE SCHEMA IF NOT
   EXISTS supabase_migrations executed as the bare login role (42501)."

NOSSO CASO:
  - Ultima migration: 20260702000003_portal_rls_validacao.sql
  - Contem: set_config('role', 'authenticated', true) na linha 209
  - SEM reset de role apos o DO block
  - Apos a migration: CLI executa INSERT INTO supabase_migrations
    schema_migrations(version, name, statements) VALUES($1, $2, $3)
  - Erro: permission denied for schema supabase_migrations (42501)

COMPATIBILIDADE: SIM — mas com mecanismo LIGEIRAMENTE DIFERENTE.

No PR #5895, o bug e: "SET ROLE postgres" e perdido por idle timeout
do pool, e o INSERT roda como o "bare login role" (role de conexao).

No nosso caso, o bug e mais direto: a ULTIMA MIGRATION ATIVAMENTE
muda a role da sessao para "authenticated" via set_config('role',
'authenticated', true). Se o CLI nao resetar a role apos a migration,
o INSERT de tracking roda como "authenticated" — que NAO tem
permissao USAGE no schema supabase_migrations.

O resultado e identico (42501 no INSERT), mas o gatilho e diferente:
  - PR #5895: idle timeout do pool perde o SET ROLE postgres
  - Nosso caso: a migration MUDA a role para authenticated e o CLI
    nao reseta
