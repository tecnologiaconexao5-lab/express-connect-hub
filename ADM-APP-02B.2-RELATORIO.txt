5. EDGE FUNCTION ofertas-publicas
----------------------------------------------------------------------------------------------------
Arquivo: supabase/functions/ofertas-publicas/index.ts
PUBLICADA: NÃO. (Código criado; nenhum deploy executado.)

5.1 Controles implementados
  - POST only; OPTIONS CORS; 405 para outros métodos.
  - CORS restrito por `OFERTAS_PUBLICAS_ALLOWED_ORIGINS` (fallback localhost).
    Origem não autorizada → 403.
  - Limite de corpo: 32 KB (Content-Length + bytes reais) → 413.
  - JSON object obrigatório; arrays/primitivos → 400.
  - Validação rigorosa via validation.ts (campos, tipos, tamanhos, enums,
    telefone/e-mail, dias, horários, modalidades, veículo, valores, LGPD).
  - Campos inesperados (tenant_id, status, protocolo, id, liberado_app etc.)
    → 400; tenant/status/protocolo nunca vêm do navegador.
  - Tenant: exclusivamente `OFERTAS_PUBLICAS_TENANT_ID` (server-side), validado
    como UUID; ausência → 503.
  - service_role: somente `SUPABASE_SERVICE_ROLE_KEY` no runtime da Edge; nunca
    retornado ao browser.
  - IP: `cf-connecting-ip`/`x-real-ip`/`x-forwarded-for`; hash SHA-256 com
    `OFERTAS_PUBLICAS_IP_SALT`; ausência do salt → 503.
  - User-Agent: hash SHA-256; opcional.
  - Idempotência: `x-idempotency-key` ou `request_id` (UUID) → p_request_id.
  - CAPTCHA: suporte Turnstile/hCaptcha; verificação server-side com timeout 5s.
    `OFERTAS_PUBLICAS_REQUIRE_CAPTCHA=true` + sem secret → 503 (não simula).
    Token inválido/expirado/reutilizado → 403 (provedor valida uso único).
  - Rate limit: aplicado dentro da RPC por tenant+IP hash (5/min); Edge mapeia
    erro `rate_limit` para 429.
  - Respostas de erro genéricas; nenhum detalhe interno/PII retornado.
  - Logs: protocolo, ip_hash_prefix, captcha_status, latência; sem CPF, telefone,
    e-mail, endereço ou payload.
  - Sucesso retorna apenas `{ success: true, protocolo }`.

5.2 Variáveis de ambiente necessárias (server-side)
  - `SUPABASE_URL` (runtime Supabase)
  - `SUPABASE_SERVICE_ROLE_KEY` (runtime Supabase; NUNCA no frontend)
  - `OFERTAS_PUBLICAS_TENANT_ID` (UUID do tenant público)
  - `OFERTAS_PUBLICAS_ALLOWED_ORIGINS` (lista separada por vírgula)
  - `OFERTAS_PUBLICAS_IP_SALT` (segredo aleatório para hash de IP)
  - `OFERTAS_PUBLICAS_CAPTCHA_PROVIDER` = turnstile | hcaptcha
  - `OFERTAS_PUBLICAS_CAPTCHA_SECRET`
  - `OFERTAS_PUBLICAS_REQUIRE_CAPTCHA=true` (produção)
  - Nenhum destes valores está hardcoded no código.

5.3 Config local
  - supabase/config.toml:
      [functions.ofertas-publicas]
      verify_jwt = false
  - Necessário para endpoint público; NÃO é deploy.

6. RPC f_registrar_oferta_publica
----------------------------------------------------------------------------------------------------
Assinatura:
  f_registrar_oferta_publica(
    p_tenant_id uuid,
    p_payload jsonb,
    p_request_id text DEFAULT NULL,
    p_ip_hash text DEFAULT NULL,
    p_user_agent_hash text DEFAULT NULL
  ) RETURNS jsonb

Segurança:
  - SECURITY DEFINER; SET search_path = public, pg_temp.
  - REVOKE ALL FROM PUBLIC, anon, authenticated.
  - GRANT EXECUTE apenas TO service_role.
  - Não há EXECUTE para anon/authenticated; o navegador não chama a RPC.

Validação/transação:
  - p_payload precisa ser objeto; allowlist de campos; rejeita tenant/status/
    protocolo/id/liberado_app e outros campos inesperados.
  - tenant existe em tenants; senão `tenant_invalido`.
  - telefone/e-mail normalizados; ao menos um contato; e-mail válido.
  - cidade/UF/regiões/dias/horários/modalidades/veículo/valores validados.
  - LGPD obrigatório; versão do termo obrigatória.
  - Protocolo não sequencial (OF-AAAAMMDD-XXXXXXXX).
  - Gravação atômica de oferta + identificadores + evento(s).
  - Retorno mínimo: success, oferta_id, protocolo, deduplicada, revisao_humana.
  - Erros por códigos genéricos (sem PII); Edge mapeia status HTTP.

Permissões:
  - Tabelas: authenticated somente SELECT/UPDATE com RLS por tenant;
    service_role ALL; anon revogado.
  - RPC: service_role only.
  - Nenhum INSERT direto para anon ou authenticated.

7. DEDUPLICAÇÃO E CONCORRÊNCIA (CORREÇÃO DO 02B.0)
----------------------------------------------------------------------------------------------------
Estratégia implementada:
  1. Normalização: telefone (dígitos), e-mail (lower), nome/cidade (trim/espaços),
     UF (upper), placa (upper), arrays ordenados, valores numéricos.
  2. Chave de identidade: não apenas a prioridade mais alta. O RPC monta
     `v_identificadores` com TODOS os disponíveis (`telefone:`, `email:`, `cpf:`/`cnpj:`)
     e adquire advisory locks transacionais para cada um, em ordem, mais o lock
     do `dedup_hash`.
  3. Duplicidade exata: `dedup_hash` canônico (tipo, nome, contato, cidade/UF,
     regiões, dias, modalidades, horário, veículo, capacidade, dimensões,
     características, valores, condições) + unique parcial `(tenant_id, dedup_hash)`
     para status ativos. Reenvio retorna o mesmo protocolo com `deduplicada=true`.
  4. Idempotência: `request_id` (UUID) em `idempotency_key` + unique parcial
     `(tenant_id, idempotency_key)`; reenvio do mesmo request retorna a mesma
     oferta/protocolo.
  5. Conflito de identificadores: consulta `recrutamento_oferta_identificadores`.
     Se telefone/e-mail/CPF apontam para mais de uma oferta distinta, a oferta é
     gravada com `revisao_humana=true` e evento `conflito_identificadores`;
     não é bloqueada automaticamente.
  6. Mesmo contato com ofertas legítimas diferentes: `dedup_hash` diferente
     (veículo/condições diferentes) e sobreposição em apenas uma oferta existente
     → oferta nova aceita sem revisão.
  7. Concorrência: advisory locks por identificador + dedup, unique parciais e
     tratamento de `unique_violation` retornando a oferta vencedora. Não depende
     de SELECT FOR UPDATE em registros inexistentes.

Limitação conhecida:
  - Os testes de concorrência reais dependem de banco com a migration aplicada.
    Nesta missão, a estratégia foi validada por contrato/fonte, não por execução
    concorrente em banco (migration não aplicada).
