ROOT CAUSE: The trigger f_trg_propagar_financeiro_alocacao creates an OS
record when an allocation is inserted WITHOUT ordem_servico_id, but
NEVER updates the allocation back to link it. The allocation's
ordem_servico_id remains NULL permanently.

Chain: Allocation (no OS) → Trigger fires → Creates OS with id=allocation.id
→ Allocation STILL has ordem_servico_id=NULL → POD trigger reads NULL →
entregas_protocolo gets ordem_servico_id=NULL.

The OS exists but is invisible to the allocation and POD chain.

SECTION 3: CUSA RAIZ — TRIGGER CRIA OS MAS NAO VINCULA
================================================================================

TRIGGER: f_trg_propagar_financeiro_alocacao
Tipo: AFTER INSERT OR UPDATE ON alocacoes_escala
Arquivo: full_production_schema_20260920.sql:12332-12437

Logica critica (simplificada):

  IF NEW.ordem_servico_id IS NOT NULL THEN
    v_os_id := NEW.ordem_servico_id;
  ELSE
    v_os_id := NEW.id;  -- ← USA O ID DA ALOCACAO COMO ID DA OS
  END IF;

  INSERT INTO ordens_servico (id, numero, ...)
  VALUES (v_os_id, 'ALOC-YYYYMMDD-XXXXXXXX', ...)
  ON CONFLICT (id) DO UPDATE SET ...;

  -- ← FALTA: UPDATE alocacoes_escala SET ordem_servico_id = v_os_id WHERE id = NEW.id;

Consequencia:
  1. Alocacao inserida SEM ordem_servico_id
  2. Trigger cria OS com id = allocation.id
  3. Alocacao PERMANECE com ordem_servico_id = NULL
  4. OS existe mas e "huferna" — invisivel para a alocacao
  5. Pod trigger (f_sync_delivery_proof_to_entregas) le ae.ordem_servico_id → NULL
  6. entregas_protocolo recebe ordem_servico_id = NULL

Prova: 68 OS existem SEM nenhuma alocacao vinculada — sao as criadas
pelo trigger para alocacoes que nunca tiveram ordem_servico_id preenchido.

SECTION 7: SOLUCAO CORREGA (DIAGNOSTICO)
================================================================================

OPCAO A — Garantir ordem_servico_id na criacao da alocacao:
  Pro: Resolve na fonte
  Contra: P1 ja tenta criar OS, mas pode falhar. P3 (AI) nao tem OS.
  Avaliacao: PARCIALMENTE VIAVEL — so para P1/P2/P4

OPCAO B — Resolver OS no trigger delivery_proofs → entregas_protocolo:
  Pro: Corrige o sintoma no ponto certo
  Contra: Trigger ja le ae.ordem_servico_id — se a alocacao nao tem,
    nao tem como resolver no trigger
  Avaliacao: NAO FUNCIONAL — o trigger ja faz o que pode

OPCAO C — Alterar fluxo APP para enviar vinculo explicito:
  Pro: APP ja envia os_id (vazio) e cliente_id (vazio)
  Contra: App e Flutter externo — nao neste repositorio
  Avaliacao: EXTERNO — requer mudanca no App Motorista

OPCAO D — Corrigir o trigger f_trg_propagar_financeiro_alocacao:
  SOLUCAO ESCOLHIDA
  Mudanca: Apos INSERT INTO ordens_servico, adicionar:
    IF NEW.ordem_servico_id IS NULL THEN
      UPDATE alocacoes_escala SET ordem_servico_id = v_os_id WHERE id = NEW.id;
    END IF;
  
  Impacto:
  - Corrige NOVOS registros (alocacao sem OS → trigger cria OS → vincula)
  - Nao afeta registros existentes (ja criados)
  - Compativel com todos os paths (P1-P6)
  - Trigger ja e SECURITY DEFINER — UPDATE e seguro
  
  Cascata:
  - Alocacao ganha ordem_servico_id
  - POD trigger le ae.ordem_servico_id → encontra OS
  - entregas_protocolo recebe ordem_servico_id correto
  - Baixas e Evidencias mostra OS ao inves de hash
  
  Limitacao:
  - 49 entregas historicas NAO serao corrigidas (ja criadas)
  - Alocacoes SEM cliente_id continuam sem OS real (trigger cria OS
    com id=alocacao mas numero "ALOC-..." que nao e OS operacional)

WHY:
  O trigger e o ponto central de criacao de OS. Ele ja cria OS para
  alocacoes sem vinculo — falta apenas o UPDATE de volta na alocacao.
  E a correcao MINIMA (3 linhas de SQL) que resolve para TODOS os
  paths de criacao de alocacao, sem alterar services, components ou
  o App Motorista.

SECTION 10: RECOMMENDED FORWARD FIX
================================================================================

RECOMMENDED_FORWARD_FIX=
  Adicionar UPDATE na funcao f_trg_propagar_financeiro_alocacao:
  Apos INSERT INTO ordens_servico, quando NEW.ordem_servico_id IS NULL:
    UPDATE alocacoes_escala SET ordem_servico_id = v_os_id WHERE id = NEW.id;

  Isso garante que TODAS as alocacoes futuras terao ordem_servico_id
  preenchido, permitindo que:
  - POD trigger leia o OS correto
  - entregas_protocolo tenha ordem_servico_id
  - Baixas e Evidencias mostre OS ao inves de hash

  NAO e necessario alterar:
  - escalaService (ja tenta criar OS)
  - Edge Function (opcional)
  - App Motorista (externo)
  - PodLista (correto em FIX-POD-01-LIST)

WHY=
  O trigger e o ponto unico de criacao de OS para alocacoes. Corrigi-lo
  resolve para todos os paths de criacao (P1-P6) com 3 linhas de SQL.
  E a solucao tecnicamente mais coerente com a arquitetura existente:
  - Nao requer mudanca no App Motorista (Flutter externo)
  - Nao requer alteracao em services TypeScript
  - Nao requer novas tabelas ou migrations complexas
  - Compativel com o comportamento existente (trigger ja cria OS)
  - Idempotente (se alocacao ja tem OS, nao faz nada)
