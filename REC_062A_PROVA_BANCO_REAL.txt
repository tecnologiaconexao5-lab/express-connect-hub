SEÇÃO 4 — SEGURANÇA RLS (VULNERABILIDADES)
═══════════════════════════════════════════════════════════════════════════════

⚠️ PROBLEMA SISTÊMICO: Policies PERMISSIVE sem cláusula USING

Todas as 4 policies de cada tabela recrutamento_* são PERMISSIVE e SEM USING:
  → Políticas PERMISSIVE sem USING = permitem acesso a TODOS os roles (incl. anon)
  → Anon (não autenticado) pode ler, escrever, atualizar e deletar dados de recrutamento
  → Isso é equivalente a RLS desligado para anon

TABELAS AFETADAS (anon bypass):
  1. recrutamento_prestadores   — anon pode CRUD completo
  2. recrutamento_candidatos    — anon pode CRUD completo
  3. crm_interacoes_prestadores — anon pode INSERT/UPDATE/SELECT (sem DELETE)
  4. candidato_documentos       — anon pode CRUD completo
  5. recrutamento_operacoes     — anon pode CRUD completo

TABELAS SEM POLICIES (RLS ON mas 0 policies = sem acesso):
  6. recrutamento_whatsapp_config      — só postgres/service_role
  7. recrutamento_whatsapp_conversas   — só postgres/service_role
  8. recrutamento_whatsapp_mensagens   — só postgres/service_role
  9. recrutamento_ia_config            — só postgres/service_role

FIX NECESSÁRIO (para 1-5):
  Para cada tabela, substituir policies por:
    USING (auth.uid() IS NOT NULL)
  Ou, se multi-tenant for necessário:
    USING (auth.uid() IS NOT NULL AND tenant_id = current_setting('app.current_tenant_id')::uuid)

FIX NECESSÁRIO (para 6-9):
  Adicionar policies para authenticated se o frontend precisa acessar.
