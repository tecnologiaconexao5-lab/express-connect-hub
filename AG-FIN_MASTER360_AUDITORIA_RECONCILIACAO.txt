3.1 FLUXO DE CRIACAO
---------------------
UI: ContasPagar.tsx → handleSalvar()
  → criarPagavel(payload) [pagarService.ts:150]
    → supabase.from("financeiro_pagar").insert(payload)
    → Colunas gravadas: descricao, valor, fornecedor, fornecedor_documento,
      documento, tipo_documento, categoria, plano_contas, centro_resultado,
      unidade_filial, despesa_fixa_base, competencia, data_emissao,
      data_vencimento, data_previsao_pagamento, valor_bruto, desconto,
      multa, juros, impostos_retidos, valor_liquido, codigo_barras,
      chave_pix, conta_pagadora, status, recorrente, observacoes

  Divergencia P0: valor (DB) vs valorLiquido (UI)
  - UI mostra: valorLiquido = valorOriginal - desconto + multa + juros - impostosRetidos
  - DB campo "valor": recebe payload.valor = valorLiquido
  - DB campo "valor_bruto": recebe payload.valor_bruto = valorOriginal
  - RPC usa: v_valor_original = SELECT valor (que e valorLiquido)
  - Conclusao: RPC calcula saldo com base em valorLiquido, NAO em valorOriginal
  - Se o titulo foi criado com valor=2005 e valor_bruto=2005 (sem desconto),
    mas depois editado para valor=2000, o saldo sera 2000 (nao 2005)

3.2 FLUXO DE BAIXA
-------------------
UI: ContasPagar.tsx → handleBaixa() [linha 561]
  → baixarPagavel(id, valor, data, conta, obs, forma) [pagarService.ts:343]
    → Fail-closed: verifica se valor não é NULL
    → RPC f_registrar_baixa_financeira({
        p_titulo_tabela: "financeiro_pagar",
        p_titulo_id: id,
        p_valor_baixado: valor,
        ...
      })
    → RPC internamente:
      1. SELECT valor, status FROM financeiro_pagar WHERE id = p_titulo_id FOR UPDATE
      2. v_valor_original = valor (coluna)
      3. v_total_baixado = SUM(valor_baixado) FROM financeiro_baixas WHERE titulo_id = p_titulo_id AND NOT estornada
      4. v_saldo = v_valor_original - v_total_baixado
      5. SE p_valor_baixado > v_saldo → ERRO "Valor da baixa excede o saldo restante"
      6. INSERT INTO financeiro_baixas
      7. UPDATE financeiro_pagar SET status, data_pagamento, data_efetiva_pgto, conta_pagadora

3.3 BUG P0 — "VALOR DA BAIXA EXCEDE O SALDO RESTANTE (2000.00)"
---------------------------------------------------------------
Causa raiz identificada:

O titulo tem valor=2000 (coluna "valor" no DB), mas a UI mostra R$ 2.005,00.

Possiveis causas:
a) O titulo foi criado com valor=2005 (valor_liquido) mas depois teve valor
   atualizado para 2000 por algum trigger ou edicao;
b) O titulo foi propagado pelo trigger M66/M80 com valor=2000, mas a UI
   calcula valorLiquido = valor_bruto - desconto + multa + juros e exibe
   um valor diferente;
c) Existe uma baixa anterior de R$ 5,00 que nao foi contada no saldo
   visivel (por ex., baixa estornada mas ainda aparecendo na UI);

No ContasPagar.tsx, o KPI "totalPagoMes" (linha 449) filtra
status === "paga" mas NAO filtra por mes — soma TODOS os pagos de
todos os tempos. Isto mascara o valor real.

A UI mostra valorOriginal (valor_bruto) como valor do titulo (linha 419):
  valorOriginal: r.valor_bruto || r.valor || 0
Mas o RPC calcula saldo usando "valor" (que pode ser diferente de valor_bruto).

Se o titulo foi criado com:
  valor_bruto = 2005, desconto = 0, valor = 2000
Entao:
  UI mostra: R$ 2.005,00 (valor_bruto)
  RPC saldo: 2000 - 0 = 2000
  Tentar baixar 2005 → ERRO (2005 > 2000)

Solucao: UI deve mostrar o valor que o RPC usa como saldo (valor), nao
valor_bruto. OU o campo "valor" deve ser igual a "valor_bruto" quando
nao ha desconto/juros/multa.

4.1 RPC f_registrar_baixa_financeira
--------------------------------------
Linguagem: plpgsql
Seguranca: SECURITY INVOKER (respeita RLS)
Transacao: SIM (mesma transacao)
Lock: SELECT ... FOR UPDATE no titulo

Fluxo:
  1. Validar valor_baixado > 0
  2. Lock titulo (FOR UPDATE)
  3. Validar status (nao cancelado, nao pago)
  4. Calcular v_saldo = valor - SUM(baixas nao estornadas)
  5. Validar v_saldo > 0
  6. Validar p_valor_baixado <= v_saldo
  7. INSERT financeiro_baixas (valor_original, valor_baixado, saldo_restante)
  8. UPDATE titulo (status, data_pagamento, conta)
  9. RETURNING saldo_restante, status_titulo

4.2 PROPAGACAO — ELO POR ELO
-----------------------------

financeiro_pagar → financeiro_baixas: ✅ INSERT direto na RPC
financeiro_baixas → contas_financeiras: ❌ NAO ATUALIZA

    calcular saldo de contas_financeiras

    somando financeiro_baixas WHERE conta_financeira_id = conta.id
  - Mas a RPC so grava conta_financeira (TEXT), nao conta_financeira_id (UUID)

contas_financeiras → Tesouraria: ❌ NAO EXISTE TELA "TESOURARIA"

  - SaldoReal = saldo_inicial + entradas(baixas) - saidas(baixas)

5.2 CALCULO
------------
balorFluxo = calcularFluxo(previstos, baixas) [fluxoCaixaService.ts:54]

  previstoEntrada = SUM(previstos WHERE tipo = "entrada")
  previstoSaida = SUM(previstos WHERE tipo = "saida")
  realizadoEntrada = SUM(baixas WHERE titulo_tabela = "financeiro_receber")
  realizadoSaida = SUM(baixas WHERE titulo_tabela = "financeiro_pagar")
  fluxoRealizado = realizadoEntrada - realizadoSaida

================================================================================
SECAO 10 — DRE (DEMONSTRACAO DO RESULTADO DO EXERCICIO)
================================================================================

10.1 REGIME: COMPETENCIA
-------------------------
A DRE usa regime de competencia (nao caixa):
  - Receita: financeiro_receber (data_vencimento no periodo)
  - Custos: pagamentos_prestadores (competencia no periodo, impacto_dre=true)
  - Despesas: financeiro_pagar (data_vencimento no periodo, exclui repasses)
  - Baixas NAO entram como competencia

10.2 LINHA POR LINHA
---------------------

Linha 1: RECEITA BRUTA
  → financeiro_receber WHERE data_vencimento BETWEEN inicio AND fim
  → Filtro: status != cancelado
  → Formula: SUM(valor) WHERE categoria = operacional
  → Fonte CANONICA: financeiro_receber

Linha 2: (-) DEDUCOES
  → financeiro_pagar WHERE categoria = "imposto"
  → Classificacao: regex /(imposto|tributo|taxa|iss|pis|cofins|irpf|csll)/
  → Fonte CANONICA: financeiro_pagar

Linha 3: = RECEITA LIQUIDA
  → Receita Bruta - Deducoes

Linha 4: (-) CUSTOS DOS SERVICOS
  → pagamentos_prestadores WHERE impacto_dre = true
  → Campo: valor_liquido
  → Fonte CANONICA: pagamentos_prestadores

Linha 5: = RESULTADO BRUTO
  → Receita Liquida - Custos Prestadores

Linha 6: (-) DESPESAS OPERACIONAIS
  → financeiro_pagar WHERE os_id IS NULL (exclui repasses)
  → Exclui categorias: "imposto" (ja em deducoes), "repasse"
  → Sub-classificacao: administrativa/comercial/outras
  → Fonte CANONICA: financeiro_pagar

Linha 7: = EBITDA
  → Receita Liquida - Custos - Despesas Operacionais

Linha 8: (-) Depreciacao e Amortizacao
  → VALOR FIXO: 0 (sem fonte de dados confiavel)
  → Impacto: EBIT = EBITDA (sempre igual)

Linha 9: = EBIT
  → EBITDA - 0

Linha 10: (+/-) Resultado Financeiro
  → Receitas Financeiras - Despesas Financeiras
  → Classificacao: regex /(financeir|juros|aplicac|rendimento)/

Linha 11: = LUCRO ANTES DO IR
  → EBIT + Resultado Financeiro

Linha 12: (-) IR e CSLL
  → VALOR FIXO: 0 (sem fonte de dados confiavel)

Linha 13: = LUCRO LIQUIDO
  → Lucro Antes IR - 0

10.3 INCONSISTENCIA COM DASHBOARD
-----------------------------------
DashboardFinanceiroEnterprise usa OS (ordens_servico) para receita:
  receitaMes = dadosMesAtual.reduce(valor_cliente)
DRE usa financeiro_receber para receita:
  receitas = financeiro_receber WHERE data_vencimento

Se uma OS foi finalizada mas a fatura ainda nao foi emitida (ou esta em
rascunho), o Dashboard mostra receita mas a DRE nao. Vice-versa.

Classificacao: BUG DE INTEGRACAO (P1)

SECAO 11 — MARGEM POR OS
================================================================================

11.1 FONTES
-------------
  Receita: composicao_financeira_os.valor_cliente
  Custo: composicao_financeira_os.valor_prestador
  Outros: composicao_financeira_os.outros_custos
    = adicional + ajudante - desconto (M66/M80)

11.2 FORMULA
--------------
  Margem R$ = Receita - Custo Prestador - Outros Custos
  Margem % = (Margem / Receita) x 100
  Status: "real" (faturado), "prevista" (valor operacional), "pendente"

11.3 PROPAGACAO
----------------
  Trigger M66 (alocacao):
    composicao_financeira_os:
      valor_cliente = valor_frete + reversa_valor_cliente
      valor_prestador = valor_repasse + reversa_valor_prestador
      outros_custos = adicional + ajudante - desconto
      origem_calculo = 'escala_direta'

  Trigger M80 (OS direta):
    composicao_financeira_os:
      outros_custos = adicionais + ajudante - descontos (JSONB extract)
      origem_calculo = 'os_direta'

11.4 PROBLEMAS
---------------
  - Se OS tem custo_prestador = 0, margem = 100% → pode ser ausencia
    de integracao, nao custo zero real
  - composicao_financeira_os e preenchida APENAS quando OS e finalizada
    (M80) ou alocacao e concluida (M66) → OS em andamento sem margem

13.1 KPIs PRINCIPAIS (DashboardFinanceiroEnterprise)
-----------------------------------------------------

KPI: "Receita do Mes"
  Valor: dadosMesAtual.reduce(valor_cliente)
  Fonte: ordens_servico WHERE status IN (finalizada, concluida) AND data >= mes_atual
  Calculo: SUM(valor_cliente)
  Confiavel: PARCIAL — usa OS, nao financeiro_receber

KPI: "Custo Prestadores"
  Valor: dadosMesAtual.reduce(custo_prestador)
  Fonte: ordens_servico (mesma query)
  Calculo: SUM(custo_prestador)
  Confiavel: PARCIAL — dados de OS, nao de pagamentos_prestadores

KPI: "Custo Geral"
  Valor: pagamentosGeral WHERE !prestador_id AND !prestador
  Fonte: financeiro_pagar WHERE status IN (aberto, a_vencer, vencido)
  Calculo: SUM(valor) EXCLUI repasses a prestadores
  Confiavel: SIM (exclui repasses corretamente)

KPI: "Resultado"
  Valor: receitaMes - custosTotais
  Fonte: calculado
  Confiavel: PARCIAL — usa OS para receita, financeiro_pagar para despesas

KPI: "Margem Operacional"
  Valor: (resultado / receitaMes) * 100
  Confiavel: PARCIAL — derivado do resultado

KPI: "Inadimplencia"
  Valor: receber WHERE status = "vencido" OR (status = "aberto" AND data_vencimento < hoje)
  Fonte: financeiro_receber
  Calculo: SUM(valor)
  Confiavel: SIM

KPI: "A Receber 7 dias"
  Valor: financeiro_receber WHERE data_vencimento BETWEEN hoje AND +7dias AND status IN (aberto, a_vencer)
  Confiavel: SIM

KPI: "A Pagar 7 dias"
  Valor: financeiro_pagar WHERE data_vencimento BETWEEN hoje AND +7dias AND !prestador_id
  Confiavel: SIM

KPI: "Repasses Pendentes"
  Valor: pagamentos_prestadores WHERE status_pagamento IN (pendente, agendado)
  Fonte: pagamentos_prestadores
  Confiavel: SIM

13.2 RECONCILIACAO KPIs
-------------------------
  Dashboard "Receita" (OS) ≠ DRE "Receita Bruta" (financeiro_receber)
    → Diferença esperada: OS sem fatura emitida
    → Se divergencia > 20%: BUG DE INTEGRACAO

  Dashboard "Custo" (OS) ≠ DRE "Custos Prestadores" (pagamentos_prestadores)
    → Diferença esperada: OS com custo estimado vs pagamento efetivo

  FluxoCaixa "Saidas Realizadas" ≠ Dashboard "Custo Geral"
    → FluxoCaixa usa baixas (pagos), Dashboard usa financeiro_pagar (pendentes)
