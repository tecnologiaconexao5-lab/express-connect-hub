4. FASE 3 — AUDITORIA f_avancar_etapa_app_motorista
────────────────────────────────────────────────────────────────

ANOMALIA A01: STABLE com UPDATE/INSERT

  Funcao contem:
    - UPDATE alocacoes_escala
    - INSERT eventos_oficiais
    - INSERT operation_timeline_events

  Mas e declarada: STABLE SECURITY DEFINER

  Risco: PostgreSQL pode rejeitar write em STABLE em replicas
  de leitura ou versoes futuras.

  CORRECAO (migration): STABLE → VOLATILE
  Corpo: IDÊNTICO ao remoto (nenhuma linha alterada)


5. FASE 4 — AUDITORIA f_atualizar_reversa_app
────────────────────────────────────────────────────────────────

ANOMALIA A02: Sem auth.uid(), autenticacao fraca

  PROBLEMA CRITICO:
    A funcao NAO usa auth.uid(). Em vez disso, faz lookup
    fraco em auth.users sem cruzar com prestador.

    Isso significa que qualquer usuario autenticado pode
    atualizar dados de reversa de QUALQUER alocacao, incluindo
    financeiro_receber e financeiro_pagar vinculados.

  TIPOS (preservados por compatibilidade):
    p_reversa_data_realizada: date (nao timestamptz)
    p_reversa_fotos:          jsonb (nao text[])
    Retorno:                  pt-BR sucesso/erro

  CORRECAO:
    Adicionado antes da logica existente:
      1. auth.uid() → NULL = USUARIO_NAO_AUTENTICADO
      2. prestadores lookup → NULL = PRESTADOR_NAO_ENCONTRADO
      3. alocacao ownership check → ALOCACAO_OUTRO_PRESTADOR
