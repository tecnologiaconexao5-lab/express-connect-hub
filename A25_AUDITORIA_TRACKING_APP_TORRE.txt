CAUSA RAIZ (bloqueador): SCHEMA DRIFT — o RPC de Produção
registrar_posicao_motorista faz INSERT em colunas que NÃO existem na tabela:

  RPC insere:  ordem_servico_id, motorista_id, altitude, status_operacional
  Tabela real: (não tem nenhuma dessas colunas — tem os_id, prestador_id, etc.)

CONSEQUÊNCIA:
- Quando o App envia uma posição, o RPC lança erro SQL
  `column "ordem_servico_id" does not exist` (não há handler EXCEPTION em volta do
  INSERT principal, linhas 128-159 da migration 20260731_fix_registrar_posicao_motorista.sql).
- O App cai no catch (_persistPosition) → posição vai para a fila OFFLINE →
  NUNCA chega a portal_tracking_realtime.
- Prova read-only: portal_tracking_realtime tem APENAS 3 linhas, NENHUMA nas
  últimas 24h; a única do prestador é de 2026-07-29 com origem 'homologacao'.

FATORES ADICIONAIS (contribuintes para o mapa vazio):
1. A OS de homologação (HML-APP-001) NÃO tem coordenadas próprias
   (localizacao_entrega_json=null, enderecos=[]) → extrairCoordenadasOS retorna null
   → o marcador NÃO é criado nem com GPS ao vivo.
2. buscarUltimasPosicoes não filtra recência/status → mesmo que o RPC funcionasse,
   posições antigas 'pendente'/'homologacao' poderiam aparecer como "atualizadas".
3. Match por os_id (TorreControle :564) depende de os_id preenchido; o RPC (se
   funcionasse) gravaria ordem_servico_id, que o TS lê como os_id — incompatível.

RESUMO:
- O fluxo App→GPS→envio→RPC está CORRETO no código do App.
- O fluxo Torre→mapa está CORRETO no código do TMS (para OS com coordenadas).
- O ELO QUEBRADO é o backend: a migration 20260731_fix_registrar_posicao_motorista
  recriou o RPC referenciando colunas que nunca foram criadas na tabela.
