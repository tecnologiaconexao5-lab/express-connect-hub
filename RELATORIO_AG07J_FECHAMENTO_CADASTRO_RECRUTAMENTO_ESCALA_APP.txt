SUMARIO EXECUTIVO
-----------------
Circuito ponta a ponta auditado em 4 subsystems:

  APP MOTORISTA --> RECRUTAMENTO (TMS) --> RECRUTAMENTO (APP) --> RECUSA
      |                                                        |
      |            +-------------------------------------------+
      |            |
      v            v
  RECUSA <-- RECUSA <-- CONTRATO <-- DISTRIBUICAO <-- ESCALA <--

Prestadores criados pelo App NAO entram automaticamente no Kanban de Recrutamento.
O App cria veiculos e prestadores diretamente no TMS (tabelas prestadores/veiculos).
O status=em_analise + liberado_app=false impede alocacao ate aprovacao manual no TMS.

2. GATE DE ELEGIBILIDADE: O QUE IMPIDE ALOCACAO
--------------------------------------------------------------------------------

Fonte: eligibilidadeOperacionalService.ts (TMS)
Arquivo: src/services/escala/eligibilidadeOperacionalService.ts

7 gates implementados (todos bloqueiam criacao de alocacao):

  GATE 1 - Status prestador:
    status != 'ativo' E status != 'aprovado' --> bloqueado
    (App sempre cria com status='em_analise' --> BLOQUEADO)

  GATE 2 - liberado_app:
    liberado_app != true --> bloqueado
    (App sempre cria com liberado_app=false --> BLOQUEADO)

  GATE 3 - Documentos (CNH validade):
    cnh_validade < hoje --> bloqueado
    cnh_validade null --> falha aberta (nao bloqueia)

  GATE 4 - Tipo veiculo (AG-07I-B1.1):
    Comparacao exata: tipo_veiculo_os == tipo_veiculo_veiculos
    Sem equivalencias (van!=kombi, van!=utilitario, etc.)
    outros != wildcard

  GATE 5 - Capacidade (AG-07I-B2):
    kg_solicitada > capacidade_kg do veiculo --> bloqueado
    m3_solicitada > capacidade_m3 do veiculo --> bloqueado
    capacidade null ou 0 --> falha aberta

  GATE 6 - Refrigerado (AG-07I-B3):
    OS carga_refrigerada=true E veiculo nao e refrigerado/termico --> bloqueado

  GATE 7 - Ajudante (AG-07I-B5):
    OS carga_ajudante=true E alocacao nao tem ajudantes --> bloqueado

resultado: App prestador SEMPRE bloqueado em todos os 7 gates porque:
  - Gate 1: status=em_analise (nao ativo/aprovado)
  - Gate 2: liberado_app=false

4. CONVERSAO CANDIDATO -> PRESTADOR (CAMINHO ENTERPRISE)
--------------------------------------------------------------------------------

Fonte: conversaoCandidatoService.ts
Arquivo: src/modules/recrutamento/services/conversaoCandidatoService.ts

Fluxo de conversao:
  1. candidato.stage == 'aprovado' ou 'ativo'
  2. buscarPrestadorOperacionalExistente() busca por telefone/email
     (AG-07G: reutiliza prestador existente do App se CPF/telefone conferem)
  3. Se existente encontrado:
     - UPDATE status=ativo, liberado_app=true, origem_cadastro='recrutamento:{id}'
     - Preenche SOMENTE lacunas (nao sobrescreve dados do App)
  4. Se NAO existe:
     - INSERT com cpf_cnpj='REC_{telefone}' (CPF real desconhecido)
     - status=statusOperacional, liberado_app=statusOperacional=='ativo'
  5. sincronizarComOperacao():
     - statusOperacional = 'ativo' se stage aprovado/ativo, senao 'analise'
     - liberado_app = statusOperacional == 'ativo'
     - origem_cadastro = 'recrutamento:{prestador_id}'

resultado_conversao:
  prestador.status = 'ativo' (se stage aprovado)
  prestador.liberado_app = true (se stage aprovado)
  prestador.origem_cadastro = 'recrutamento:{id}'
  Se reutilizou App prestador: dados do App preservados (CNH, telefone, etc.)

5. SINCRONIZACAO KANBAN -> OPERACAO (APROVACAO)
--------------------------------------------------------------------------------

Fonte: prestadoresService.ts
Arquivo: src/modules/recrutamento/services/prestadoresService.ts

Quando gestor aprova candidato no Kanban:
  1. syncAtualizarOperacional() e chamada
  2. Status operacional derivado:
     - agregado/aprovado -> 'ativo'
     - bloqueado -> 'inativo'
     - outro -> 'analise'
  3. UPDATE prestadores SET:
     status = novoStatus
     liberado_app = novoStatus == 'ativo'
     nome_completo, telefone, whatsapp, tipo_parceiro
     endereco = {cidade, estado}
     veiculos = [{tipo, placa}]
  4. origem_cadastro = 'recrutamento:{prestador_rec_id}'

resultado_sincronizacao:
  prestador.status = 'ativo' (se aprovado)
  prestador.liberado_app = true (se aprovado)
  PRESTADOR DO APP: dados preservados, status e liberado_app sobrescritos

8. GAPS IDENTIFICADOS
--------------------------------------------------------------------------------

GAP J-1: APP PRESTADORES NO KANBAN
  Severidade: MEDIA
  Descricao: App prestadores com status='em_analise' NAO aparecem no Kanban.
  Impacto: Gestor nao ve candidatos que ja se cadastraram pelo App.
  Solucao: Bridge entre prestadores (origem_cadastro='app_motorista') e
           recrutamento_candidatos, OU exibicao especial no Kanban.

GAP J-2: DOCUMENTOS PENDENTES
  Severidade: ALTA
  Descricao: App NAO envia documentos (CNH, antt). Somente veiculo e dados pessoais.
  Impacto: Prestador do App fica permanentemente bloqueado no Gate 3
           (cnh_validade null = fail-open, mas sem documentos reais).
  Solucao: Upload de documentos pelo App apos cadastro inicial.

GAP J-3: ANTT SEM GATE
  Severidade: BAIXA (AG-07I-B4)
  Descricao: campo antt populado pelo App mas sem validacao de estrutura/validade.
  Impacto: Veiculos com antt invalido passam pela escala sem verificacao.
  Solucao: Gate de ANTT (aplicabilidade + validade) - DEPENDENCIA ESTRUTURAL.

GAP J-4: RPC f_buscar_operacoes_motorista NAO APLICADA EM PRODUCAO
  Severidade: ALTA
  Descricao: Migration AG-07F (20260822_ag07f_gate_elegibilidade_operacional.sql)
           NAO foi aplicada em producao. RPC em producao usa versao antiga.
  Impacto: Operacoes criadas ANTES da aprovacao podem aparecer no App
           (versao antiga nao filtra por status/liberado_app).
  Solucao: Aplicar migration em producao.

GAP J-5: POSSUI_AJUDANTE = METADADOS
  Severidade: BAIXA (AG-07I-B5)
  Descricao: App preenche _possuiAjudante (booleano) mas NAO e campo estruturado
           na tabela prestadores. E informacao de metadata apenas.
  Impacto: Nenhuma validacao automatizada e possivel.
  Solucao: Campo estruturado na tabela prestadores - DEPENDENCIA ESTRUTURAL.

GAP J-6: DUAS TABELAS DE RECRUTAMENTO
  Severidade: MEDIA
  Descricao: Duas tabelas de recrutamento:
           - recrutamento_candidatos (Kanban Enterprise)
           - prestadores (Operacao + App)
           Nao ha sincronizacao automatica entre elas.
  Impacto: Dados duplicados, inconsistencias, gestor confuso.
  Solucao: Consolidar em uma unica tabela ou criar sync.

GAP J-7: RECRUTAMENTO LEGACY PATH
  Severidade: BAIXA
  Descricao: Ha path legado (recrutamentoIntegracao.ts) que usa
           portal_pedidos + portal_preferencias. Sem synchronizacao
           automatica com Kanban Enterprise.
  Impacto: Dados legados podem ficar inconsistentes.
  Solucao: Deprecar path legado.

GAP J-8: SEM TRIGGER ATUALIZACAO APP -> RECRUTAMENTO
  Severidade: MEDIA
  Descricao: Quando App prestador muda status/doc, NAO ha trigger que
           atualize recrutamento_candidatos (se existir).
  Impacto: Kanban fica desatualizado.
  Solucao: Trigger ou listener de mudancas em prestadores.

14. CONCLUSAO
--------------------------------------------------------------------------------

O circuito App --> Recrutamento --> Escala --> Operacao tem DUAS ROTAS:

  ROTA A (App): App cadastra --> prestadores (em_analise, liberado=false)
    --> SEM Kanban, SEM documentos --> BLOQUEADO ate aprovacao manual

  ROTA B (Enterprise): Candidato --> recrutamento_candidatos --> Kanban
    --> Aprovacao --> conversaoCandidatoService --> prestadores (ativo, liberado=true)
    --> Alocacao PERMITIDA

  AMBAS as rotas convergem em prestadores.status + liberado_app.

  O GATE funciona: prestador do App NAO pode ser alocado sem aprovacao.
  POREM: App prestador e INVISIVEL no Kanban (gap J-1).
  E: App prestador NAO tem documentos (gap J-2).

  FECHAMENTO: Circuito INCOMPLETO mas funcional para aprovacao manual.
  Necessario: Bridge App-Kanban + upload documentos.
