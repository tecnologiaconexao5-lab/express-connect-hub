  Sessão A e Sessão B chamam f_confirmar_pagamento_fechamento(X):
    - A adquire lock no fechamento primeiro.
    - B espera.
    - A processa todos os itens, insere baixas, atualiza status,
      commita.

    - Resultado: 1 baixa total. ✅

  ⚠️  Não há lock explícito de financeiro_pagar compartilhado entre
     fechamentos diferentes. Se um mesmo item aparecer em dois
     fechamentos (violação de modelo), poderia haver race. Modelo
     atual garante 1:1, então risco é BAIXO.

  Classificação: risco MÉDIO/BAIXO — não bloqueia homologação, mas
  pode ser endurecido com advisory lock no futuro.

============================================================

Tabela: public.fin_sane_02b_snapshot

6.1 O QUE FUNCIONA
  ✅ Snapshot acontece ANTES do UPDATE (INSERT snapshot → depois UPDATE).
  ✅ IDs permitem rollback exato (financeiro_pagar_id).
  ✅ valor_anterior e valor_novo registrados.
  ✅ Somente registros elegíveis entram no snapshot.
  ✅ Migration não destrói dados históricos.

6.2 FRAGILIDADES IDENTIFICADAS
  ⚠️  CTE do UPDATE usa DISTINCT ON (financeiro_pagar_id) sem ORDER BY.
      Se houver snapshots duplicados, a linha escolhida é não
      determinística (embora valor_novo seja igual na mesma batch).
  ⚠️  Filtro s.processado_em >= MAX(processado_em) funciona porque
      NOW() é constante dentro de uma transação, mas é frágil se a
      migration for executada em batches próximos.
  ⚠️  Filtro s.valor_novo >= 0 pode excluir valores negativos de
      pp.valor_liquido, criando inconsistência snapshot vs UPDATE.
  ⚠️  INSERT no snapshot não previne duplicatas em reaplicação.

6.3 SEGURANÇA
  ⚠️  Snapshot não possui RLS. Dados são financeiramente sensíveis.
      Recomendação pós-homologação: adicionar RLS e/ou restringir
      acesso a service_role/super_admin.

6.4 CONCLUSÃO
  Snapshot funciona para rollback, mas deve ser endurecido antes de
  produção (B1).
