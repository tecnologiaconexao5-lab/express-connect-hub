CAUSA RAIZ
----------
O sistema permitia criar/atualizar financeiro_receber com status='pago'/'recebido'/'baixado'
sem exigir uma baixa correspondente em financeiro_baixas. Isso ocorria porque:

1. receberService.criarRecebivel() aceitava status='pago' no input
2. receberService.atualizarRecebivel() permitia transição para 'pago' via update direto
3. Não havia trigger no banco que validasse a existência de baixa
4. A UI (ContasReceber/ContasReceberEnterprise) permitia salvar com status='pago'

ALTERAÇÕES REALIZADAS
---------------------

1. BACKEND (receberService.ts):
   - Adicionado STATUS_PAGO_SEM_BAIXA = ["pago", "recebido", "baixado"]
   - Adicionado validarStatusCriacao(): bloqueia criarRecebivel com status pago
   - Adicionado validarStatusAtualizacao(): bloqueia atualizarRecebivel com status pago
   - Aplicado em: criarRecebivel, criarRecebiveisEmLote, atualizarRecebivel

2. BANCO (migration 20260906_fin_master_363a3_bloqueio_receber_pago_sem_baixa.sql):
   - Criado trigger trg_guardar_receber_pago_sem_baixa
   - BEFORE INSERT OR UPDATE OF status ON financeiro_receber
   - Valida existência de baixa não estornada em financeiro_baixas
   - RAISE EXCEPTION se tentar marcar como pago sem baixa
   - Aplicado com sucesso no Supabase real

3. UI (ContasReceber.tsx e ContasReceberEnterprise.tsx):
   - Formulário de edição não permite mais salvar com status='pago'
   - Usuário deve usar o botão oficial "Dar Baixa" que chama baixarRecebivel()
