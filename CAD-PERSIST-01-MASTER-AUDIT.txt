SECAO A — PERSISTENCIA DO FORMULARIO PRESTADOR/MOTORISTA
---------------------------------------------------------

Arquitetura do Fluxo Prestador:
  CadastrosPrestadores.tsx (page, rota /cadastros-prestadores)
    ├── view="lista" → PrestadoresLista.tsx (componente)
    ├── view="detalhe" → PrestadorDetalhe.tsx (componente)
    └── view="novo" → PrestadorDetalhe.tsx (componente)

O componente "page" usa useState<"lista"|"detalhe"|"novo"> para alternar.
Pre存cia: NENHUM service layer dedicado. Supabase chamado DIRETO do form.

Fluxo de Criacao/Edicao:
  1. PrestadoresLista carrega: supabase.from('prestadores').select('*').range(from, to)
  2. Usuario clica "Novo Prestador" → view="novo" → PrestadorDetalhe montado
  3. PrestadorDetalhe usa useState<Partial<Prestador>> para TODOS os campos
  4. Upload de documentos vai para Supabase Storage ANTES do INSERT principal
  5. handleSave faz INSERT ou UPDATE direto no Supabase (sem service layer)
  6. Sucesso: toast.success + onBack() → volta para lista
  7. Falha: try/catch + setErro/toast.error

Riscos Identificados:
  - Sem validacao antes de salvar (PrestadorDetalhe: handleSave nao valida nada)
  - Sem beforeunload, sem useBlocker, sem exit guard
  - Click "Voltar" ou sidebar perde TODOS os dados nao salvos
  - Upload de documentos pode criar arquivos orfas no Storage se INSERT falhar
  - Lista nao tem refresh trigger explicito (remount mitigates parcialmente)

    trg_propagar_financeiro_alocacao → financeiro (NÃO toca prestadores)
    trg_cancelar_financeiro_alocacao → financeiro (NÃO toca prestadores)
    trg_evento_* → eventos_oficiais (log apenas, NÃO toca prestadores)
    trg_registrar_historico_alocacao → historico (log apenas)

  NENHUM trigger em alocacoes_escala ou ordens_servico faz:
    UPDATE prestadores SET qtd_operacoes = qtd_operacoes + 1
    UPDATE prestadores SET score_interno = ...
    Qualquer outra atualizacao de indicadores

  Triggers na tabela prestadores:
    update_prestadores_updated_at → so atualiza updated_at
    trg_bridge_prestador_para_recrutamento → insere em recrutamento_prestadores

  Resultado: Todas as colunas de indicadores ficam com DEFAULT 0 para SEMPRE.

  40 prestadores no total

  0 com score_interno > 0
  0 registros em prestadores_ocorrencias

  NENHUM dos 56 registros concluidos atualizou indicadores do prestador

Indicadores Fonte (de onde OS DADOS REAIS deveriam vir):
  Total Entregas: COUNT de alocacoes WHERE prestador_id=X AND status='concluida'
  Ocorrencias: COUNT de prestadores_ocorrencias WHERE prestador_id=X
  Score: MEDIA de avaliacoes em entregas_protocolo ou portal_avaliacoes
  Indice Aceite: COUNT(aceite_prestador=true) / COUNT(*) WHERE prestador_id=X
  Indice Prazo: COUNT(data_fim_real <= data_previsao_fim) / COUNT(*)
  Indice Comparecimento: COUNT(presenca_confirmada=true) / COUNT(*)
